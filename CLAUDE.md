# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Environment

- **Liferay version**: `portal-7.4-ga132` (defined in `gradle.properties`)
- **Workspace product**: Liferay 7.4 — use traditional OSGi modules (Service Builder, REST Builder). Client Extensions are available but the core product is module-based.
- **CLI**: Always use `blade gw` for Gradle tasks, never invoke `./gradlew` directly.

## Key Commands

```bash
# Code generation (run after modifying service.xml or rest-openapi.yaml)
blade gw buildService          # Regenerates Service Builder code
blade gw buildRest             # Regenerates REST Builder code

# Build & deploy
blade gw deploy                # Build and deploy all modules to the running bundle
blade gw :modules:product-service:product-service-service:deploy  # Deploy single module

# Code formatting (MUST run before committing)
blade gw formatSource

# Unit tests (fast, no server needed)
blade gw :modules:product-service:product-service-service:test

# Integration tests (requires running Liferay bundle at bundles/)
blade gw :modules:product-service:product-service-test:testIntegration
blade gw :modules:product-rest:product-rest-test:testIntegration

# Watch mode (auto-redeploy on changes)
blade gw watch
```

## Module Architecture

Two Service Builder + REST Builder modules:

### `modules/product-service/`
| Sub-module | Purpose |
|---|---|
| `product-service-api` | Generated interfaces, model, exceptions — consumed by other modules |
| `product-service-service` | `ProductLocalServiceImpl` — business logic, persistence, indexer |
| `product-service-test` | Arquillian integration tests against the live bundle |

**Entity**: `Product` — fields: `name`, `description`, `price` (double), `status` (int), `stockQuantity` (int), plus standard Liferay audit fields. Finder: `findByGroupId`. References: `AssetEntry`, `AssetTag`.

Status lifecycle: `DRAFT (0) → PUBLISHED (1)`, `INACTIVE (2)`. Status controls AssetEntry visibility.

### `modules/product-rest/`
| Sub-module | Purpose |
|---|---|
| `product-rest-api` | Generated DTO and resource interfaces from `rest-openapi.yaml` |
| `product-rest-impl` | `ProductResourceImpl` — delegates to `ProductLocalService` |
| `product-rest-client` | Auto-generated Java client (do not edit) |
| `product-rest-test` | Arquillian integration tests (currently placeholder) |

**API base path**: `/o/product-rest/v1.0/sites/{siteId}/products`

Additional endpoints: `PUT /products/{productId}/categories`, `PUT /products/{productId}/tags`

## Generated Code Rules

- **Never manually edit** files under `product-service-api/` or `product-rest-api/` — they are regenerated by `buildService`/`buildRest`.
- Business logic belongs exclusively in `*LocalServiceImpl` (service-service module) and `*ResourceImpl` (rest-impl module).
- After modifying `service.xml`: run `buildService`, then commit the generated files in a separate `chore:` commit.
- After modifying `rest-openapi.yaml`: run `buildRest`, then commit generated files separately.

## Integration Test Patterns

Tests use **JUnit 4 + Arquillian** (not JUnit 5). Key conventions:

```java
@RunWith(Arquillian.class)
public class ProductLocalServiceIntegrationTest {

    @ClassRule
    @Rule
    public static final AggregateTestRule aggregateTestRule =
        new AggregateTestRule(
            new LiferayIntegrationTestRule(),
            PersistenceTestRule.INSTANCE,
            new TransactionalTestRule(
                Propagation.REQUIRED, "product.service.service"));

    @Before
    public void setUp() throws Exception {
        _group = GroupTestUtil.addGroup();
        _user = UserTestUtil.addUser();
    }

    @After
    public void tearDown() throws Exception {
        // cleanup group, user, products
    }
}
```

- Always use `ServiceContextTestUtil.getServiceContext(_group.getGroupId(), _user.getUserId())` to build `ServiceContext`.
- Tests must clean up all created entities in `@After` to avoid data leakage between test runs.
- Use `@InjectMocks` + Mockito for unit tests in `product-service-service`; use Arquillian for integration tests in `product-service-test`.

## Commit Conventions

Follow Conventional Commits with scope:

```
feat(product-service): add low-stock threshold validation
fix(product-rest): correct status filter query param mapping
test(product-service): add integration test for inactive status
chore(product-service): regenerate Service Builder code after adding stockQuantity field
build: update test configurations
```

Separate generated-code commits (`chore:`) from feature/fix commits.
